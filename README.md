# Agent Workspace

Переносимые проекты и краткое состояние задач для Codex. MCP-сервер хранит записи и готовые результаты в обычной синхронизируемой папке. Synology Drive, Google Drive или другой файловый клиент доставляет её между ПК.

Исходники проектов остаются локально. Агент сохраняет цель, этапы, решения, уверенность и основания, проверки, незавершённые вопросы и следующий шаг. Полный чат по умолчанию не переносится.

## Установка готового комплекта

1. Установите Codex и клиент синхронизации. Дождитесь загрузки существующей общей базы `AI-Workspace` с файлом `workspace.json`.
2. Полностью распакуйте готовый `Agent-Workspace-Setup.zip` из Releases в локальную папку.
3. Прочитайте `0_Описание.rtf`.
4. Приложите `1_Установка_агента.md` в чат Codex и напишите: «Установи правила агента по приложенной инструкции».
5. Приложите `2_Установка_MCP.md` и напишите: «Установи MCP Agent Workspace по приложенной инструкции».
6. В появившемся окне выберите существующую `AI-Workspace`. Агент сам проверит и распакует программу, настроит подключение и сохранит резервные копии. После обоих шагов один раз перезапустите Codex и проверьте MCP.

Первый файл добавляет инструкции уже установленному Codex. Приложение Codex в комплект не входит. Готовый Windows x64 runtime Node.js включён в пакет MCP.

## Использование

- **«Начни работу»** — проверить доставленные версии, загрузить принятую запись задачи и выбранные готовые файлы.
- **«Закончи работу»** — проверить все доступные чаты Codex, включая архив, и сохранить отдельные записи продолжения только для изменившихся чатов.
- **«Закончи работу только этот чат»** — ограничить сохранение текущим чатом.
- При расхождениях агент показывает сравнение и рекомендацию; основную версию выбирает пользователь.

Окончание сессии не означает завершение всей задачи. Успешная запись в локальную папку не подтверждает доставку на NAS или другой ПК. Таймера и автоматического перехвата закрытия окна нет.

Для каждого чата сохраняется граница обработки: ID последнего шага/сообщения и контрольная сумма видимого содержимого. Следующая проверка читает хвост истории; при изменении загружает новые шаги до сохранённой границы. Номер строки не используется: сжатие, откат и изменение истории могут сдвинуть строки. Одинаковые дата и размер не доказывают отсутствие изменений.

Неизменившийся чат пропускается до подготовки сводки. Идентичный handoff также не создаёт новую ревизию. При первом сохранении сводку формирует агент из доступной истории; ограниченное чтение отмечается как неполное. Скрытые рассуждения, вывод инструментов, авторизация и полная переписка в общую базу не копируются.

Охват — доступные этому ПК чаты Codex. Архив проверяется отдельно; удалённые и недоступные хосты указываются в отчёте. Чат на другом ПК будет обработан там после запуска процедуры. Чаты, в которых продолжается работа, остаются ожидающими следующей проверки. Раннее изменение до неизменившейся границы нельзя гарантированно обнаружить без полной проверки истории.

## Данные и архитектура

- `src/store.js` — история ревизий, контрольные суммы, сравнение, выбор версии, готовые объекты и восстановление.
- `src/server.js` — 12 MCP-инструментов через stdio, включая проверку всех чатов и сохранение выбранной сводки.
- `src/chat-source.js` — чтение доступных чатов через Codex App Server и сравнение хвоста истории.
- `src/chat-sync.js` — устойчивая привязка чата к задаче, локальные снимки и указатель последней обработанной границы.
- `src/schema.js` — структура и проверки handoff.
- `src/codex.js`, `src/vault.js` — переносимые описания настроек, локальные привязки и отдельный шифрованный vault.
- `native/FolderPicker.cs` — стандартное окно выбора папки Windows.
- `packaging/simple/` — переносимые инструкции установки и описание комплекта.

## Разработка

Для ядра нужны Node.js 22+ и pnpm. Версии зависимостей зафиксированы в `pnpm-lock.yaml`.

```text
pnpm install --frozen-lockfile
node scripts/check.js --suite core
node scripts/check.js --suite protocol
node scripts/check.js --suite credentials
```

Проверки используют синтетические данные в `work/`, оставляют наблюдения для осмотра и не удаляют каталоги рекурсивно. Они не изменяют реальные настройки Codex или общую пользовательскую базу. Готовые `node.exe`/ZIP и рабочие данные не хранятся в Git.

## Сборка Windows x64

Сборка выполняется на Windows x64. Нужны Node.js 22+, pnpm и штатный C# compiler .NET Framework 4.x по пути `%SystemRoot%/Microsoft.NET/Framework64/v4.0.30319/csc.exe`. Для простого установочного комплекта дополнительно нужен Python 3.10+; внешние Python-пакеты не используются.

```text
pnpm build
node scripts/verify-release.js
python scripts/build-kit.py
```

Результаты создаются в `output/`: отдельный готовый runtime, его ZIP, простой комплект `Agent-Workspace-Setup/` и общий ZIP с SHA-256. Каталоги и архивы сборки не перезаписываются молча. Для повторного выпуска используйте чистое место сборки или сохраните прежние результаты отдельно.

При необходимости отдельно выполните `scripts/smoke-release.ps1` через PowerShell 7. Это запуск готового CLI/stdio на синтетических данных, а не проверка другого физического ПК. Сборка не подтверждает работоспособность реальной облачной доставки.

## Локальная командная строка

Для исходников: `node src/app.js help`. Для готового пакета: `agent-workspace.cmd help`.

Основные команды: `init`, `attach`, `startup`, `project`, `get`, `save-task`, `review`, `choose`, `result`, `package`, `restore`, `serve`. Команда `init` создаёт новую пустую базу, `attach` подключает существующую. Для исходного CLI путь можно передать через `--root`; графический helper поставляется с готовым Windows-пакетом.

Для чтения чатов один раз укажите настоящий установленный Codex этого ПК:

```text
agent-workspace.cmd configure-chat-reader --codex ABSOLUTE_INSTALLED_CODEX_EXE --home ACTUAL_CODEX_HOME --local LOCAL_STATE
agent-workspace.cmd scan-chats --input LOCAL_SCAN_OPTIONS_JSON --local LOCAL_STATE
agent-workspace.cmd save-chat --input LOCAL_HANDOFF_JSON --local LOCAL_STATE
```

Все обозначения путей заменяются реальными абсолютными путями. `--home` необязателен; при его использовании нужен действительный каталог Codex, а не копия авторизации. Конфигурация читателя остаётся только в `LOCAL_STATE/codex-reader.json`. Читатель использует операции чтения App Server, без вызова модели и изменения чатов.

В 0.3.1 для читателя используется стабильный путь запуска установленного Codex, который может проходить через управляемый приложением junction. Перед каждым открытием выбранный исполняемый файл разрешается в действительный физический путь и проверяется там. При обновлении Codex с заменой цели такого launcher повторная ручная привязка не нужна. Не закрепляйте вместо него временный каталог конкретной версии. Это исключение относится только к выбранному исполняемому файлу Codex: запрет ссылок/junction в общей базе, локальном хранилище и пакетах сохраняется.

Сначала используется уже настроенный корректный путь Codex. Только при его отсутствии или отсутствии файла выполняется ограниченный поиск: абсолютные каталоги PATH и известные каталоги установки текущего пользователя (включая Programs/OpenAI/Codex/bin и packages/standalone/current/bin действительного CODEX_HOME). Кандидаты объединяются по физическому файлу. Единственный найденный вариант можно использовать; CODEX_PATH_REQUIRED означает, что нужно выбрать папку установки/исполняемый файл, а CODEX_PATH_AMBIGUOUS — что нужно выбрать из нескольких установок. Версию автоматически не выбирают, диски целиком не сканируют, авторизацию не ищут.

На другом ПК или после переноса папок пути определяются заново: codex-reader.json и device.json остаются локальными и между ПК не копируются. Общая папка подключается через attach с проверкой workspace_id; пользовательские абсолютные пути не становятся общими настройками.

MCP `workspace_scan_chats` возвращает `run_id` и `next_offset`: ими продолжают обход зафиксированного списка до последней страницы. Передайте `current_session_id` и известные по приложению `active_session_ids`, поскольку отдельный процесс чтения не видит надёжно всю текущую работу интерфейса. При `pending_history` или `partial` нельзя продвигать сохранённую границу: сначала требуется дополнительное чтение. Для расширения чтения есть `inspect_options.maxTurns`, `maxCharacters` и `fullAudit`; ограничения всё равно проверяются по фактическому покрытию. При изменении или исчезновении границы полный аудит может вернуть `needs_history_review`: после полного чтения покажите изменения и обновлённую сводку человеку. Только его явное одобрение разрешает `workspace_save_chat` с `history_reviewed_by_user: true`. Обычный прирост и завершение текущего шага inProgress → completed не требуют такого подтверждения; изменение ранее завершённой истории требует проверки. Новые чаты и сообщения после снимка проверяются следующим запуском.

## Ограничения

MCP не является облачным синхронизатором и не содержит собственной модели ИИ. Сводку формирует агент. Авторизация приложений, OAuth-кеши и рабочие БД не клонируются. Переносимые статические секреты можно сохранять отдельно в зашифрованном vault; пароль не хранится рядом и не передаётся через чат или аргументы команды.

Контрольные суммы показывают целостность, а не автора. Проверки путей уменьшают риск перенаправления через symlink/junction, но не являются транзакционной защитой от активной подмены другим процессом. Полный цикл на втором физическом ПК проверяется отдельно.
