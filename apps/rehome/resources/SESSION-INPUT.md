# Подготовка сводок агентом

Этот контракт предназначен для агента команды «Закончи работу». Пользователь не должен вручную заполнять JSON. ReHome не вызывает другую модель и не хранит API-ключи. Сводки готовит текущий агент до закрытия Codex.

Вход `prepare`: объект с тремя полями `inspection`, `source`, `include_environment` (boolean). `inspection` — точный объект из действия `inventory`, без изменения границ. Все идентификаторы состоят из ASCII букв, цифр, `_` или `-`, начинаются с буквы/цифры, не более 96 знаков. Источник сжимается только в переносимом представлении; исходные чаты не редактируются.

`source` содержит:

- `workspace_id`: из inspection, не ID другой базы Workspace.
- `created_at_ms`: дата создания сводки, Unix milliseconds. Это дата сообщения-сводки; даты карточек берутся из каталога.
- `catalog`: точная копия `inspection.catalog`. В ней `projects` с `id,name,created_at_ms,updated_at_ms`; `chats` с `canonical_chat_id,title,project_id,archived,is_pinned,created_at_ms,updated_at_ms`. Не теряй пустые проекты и архивные чаты. Канонический ID не меняется при переименовании или переносе.
- `handoffs`: ровно одна запись на каждый каталогизированный чат, включая неполные случаи.
- `results`: последние выбранные версии готовых результатов. Папки исходников, рабочие репозитории и авторизация сюда не включаются.

Запись `handoffs` имеет ровно поля:

```json
{
  "canonical_chat_id": "CHAT-ID",
  "task_record_id": "TASK-ID",
  "task_revision_id": "SUMMARY-REVISION-ID",
  "source_cursor": {"last_turn_id": "TURN-ID", "visible_sha256": "64-lowercase-hex"},
  "coverage": "complete",
  "goal": "Цель работы",
  "outcome": "Полученный результат",
  "decisions": [{"text": "Принятое решение", "reason": "Краткое основание и существенная неопределённость"}],
  "constraints": ["Сохраняемые ограничения"],
  "unfinished": ["Открытый вопрос"],
  "next_steps": ["Следующее действие"]
}
```

Это пример формы, не реальные данные: строки `64-lowercase-hex` и `CHAT-ID` заменяются наблюдаемыми значениями. source_cursor берётся из соответствующей inspection.boundaries; при отсутствии видимых ходов last_turn_id равен `no-visible-turns`, coverage обязательно `partial`. `complete` разрешён только после фактического чтения нужной истории и принятых сводок. Хеш границы сам по себе не доказывает, что агент прочитал сообщения. Не скрывай ограничения покрытия.

Для чата, уже перенесённого ReHome, сохрани task_record_id из принятого handoff. Для первого локального сохранения используй устойчивый UUID задачи и сохраняй его в следующих публикациях. task_revision_id обозначает версию handoff; можно получить SHA256 нормализованного содержимого сводки. Имена этих полей совместимы с прежними handoff: ссылки на запись/ревизию внешнего Workspace — только происхождение. Они не разрешают автоматически переключать Workspace selected.json.

Запись `results` имеет ровно поля:

```json
{
  "result_id": "LOGICAL-RESULT-ID",
  "version_id": "VERSION-ID",
  "project_id": "PROJECT-ID",
  "chat_ids": ["CHAT-ID"],
  "name": "Отчёт.pdf",
  "source_path": "C:/Users/Example/Documents/Отчёт.pdf",
  "relative_path": "Projects/PROJECT-ID/Results/LOGICAL-RESULT-ID/Отчёт.pdf",
  "sha256": null,
  "bytes": null
}
```

`sha256` и `bytes` заполняются фактическим хешем и размером существующего файла. Оба `null` допустимы только во входе подготовки для отсутствующего файла; Finish отразит пропуск. В опубликованном пакете каждый результат имеет реальные байты, размер и хеш.

Один result_id — один логический результат и только последняя выбранная версия. Разные одноимённые результаты получают разные result_id и каталоги. Порядок версии определяется последовательностью фактической выдачи в чате, не mtime. Не угадывай связь разных документов. `project_id` равен проекту всех перечисленных chat_ids; для чата вне проекта — null и путь `Projects/__projectless__/Results/...`. Пути относительные, без `..`, обратных слешей и выходов из пакета. Исходный абсолютный путь хранится как происхождение; при восстановлении ссылки в сгенерированном разделе результатов заменяются адресами получателя.

При подготовке новой сводки сохраняй значимые решения и ограничения принятой, добавляй фактически прочитанный прирост. Не вставляй прежние неработающие ссылки вместо раздела `results`. Недоступные старые результаты и неопределённые связи укажи явно в `unfinished`; пользователь не должен отдельно разбирать каждый такой случай до сборки.

После prepare запускается finish с возвращёнными `request` и `request_sha256`. Помощник проверяет сохранённые префиксы. Новые сообщения за границей попадут в отчёт как не включённые; изменение уже прочитанного префикса останавливает сборку. Для восстановления используются только проверенные полные публикации, а недостаточное содержание сводки не выдаётся за полную историю.
